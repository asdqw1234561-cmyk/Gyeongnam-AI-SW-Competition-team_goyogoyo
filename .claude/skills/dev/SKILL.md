# /dev — 개발 Agent 작업 절차

요청: **$ARGUMENTS**

요청이 비어 있으면 무엇을 할지 한 문장으로 물어보고 멈춘다.
요청이 "어떻게 만드는 게 좋을까?" 같은 설계 질문이면 2~3단계만 하고 설계안을 제안한 뒤 멈춘다(코드 수정 금지).

## 1. 상태 확인
- `git branch --show-current`, `git status --short`를 실행한다.
- 작업자 본인 브랜치가 아니거나, 이번 요청과 무관한 미커밋 변경이 있으면 멈추고 알린다.

## 2. 현재 구현 파악
- 요청과 관련된 파일을 실제로 읽는다. 사용자의 설명이나 기억에 의존하지 말고 코드로 검증한다.
- 재사용할 기존 함수, 데이터 흐름, 관련 테스트 파일을 찾는다.
- CLAUDE.md의 원칙과 충돌하는지 확인한다(Python이 숫자 담당, 미확보 표시, 승인 전 적용 금지, 좌표·반경은 Python 소유, 직선거리 표현, 점수 계산식 불변 등).

## 3. 계획
- 수정할 파일과 이유를 3~6줄로 정리한다. 수정 범위는 최소로 한다.
- 기존 기능의 의미가 바뀌거나(계산식, 화면 문구의 의미, 데이터 해석), 원본 데이터·`analysis/scoring.py` 계산식을 건드려야 하면 구현 전에 사용자에게 보고하고 확인을 받는다.
- 그 외에는 확인 없이 바로 진행한다.

## 4. 구현
- 기존 함수를 재사용하고, 같은 계산을 여러 파일에 중복 구현하지 않는다.
- 데이터 수치를 하드코딩하지 않는다. 비밀키를 코드에 넣지 않는다.
- 주변 코드의 주석 밀도·이름 규칙·스타일을 따른다.
- 새 동작에는 단위 테스트를 추가한다. 실제 AI 호출은 모킹한다(`ollama.chat`, `subprocess.run` 등).

## 5. 테스트
- 관련 테스트 → 전체 테스트 순서로 실행한다:
  `python -m unittest tests.<관련모듈> -v` → `python -m unittest discover -s tests`
- 실패하면 원인을 고치고 다시 돌린다. 테스트 기대값을 실패에 맞춰 바꾸는 것은 기능 의미가 바뀐 경우에만 하고 이유를 보고한다.
- 화면에 영향이 있으면 가능한 범위에서 Streamlit 실행 확인을 하고, 못 했으면 "브라우저 수동 확인 필요"로 남긴다.
- (작업을 끝낼 때 Stop hook이 바뀐 .py가 있으면 전체 테스트를 다시 돌린다. 실패하면 종료가 막히니 고쳐서 마무리한다.)

## 6. 검토와 보고
- `git diff --stat`과 `git diff`로 변경 내용을 직접 검토한다. 요청과 무관한 변경이 섞였으면 되돌린다.
- 아래 형식으로 보고한다:

```
## 결과
<무엇이 어떻게 바뀌었는지 1~3문장>

## 변경 파일
- path:line — 무엇을 왜

## 테스트
- 모킹 단위 테스트: <실행한 명령> → <결과>
- 실제 Claude/Ollama 호출: <했으면 결과 / 안 했으면 "미실행">
- 화면 확인: <결과 / "브라우저 수동 확인 필요">

## 확인하지 못한 것 / 남은 일
- ...
```

- 실제로 실행·확인한 것만 "통과/확인"이라고 쓴다.
- commit은 사용자가 요청할 때만 한다. 요청받으면 `git push origin <본인 브랜치>`까지 한다(force push 금지).
